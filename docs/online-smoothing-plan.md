# 联机平滑同步 + 新加坡服务器（2026-11-19）

## 现状（Research）

- 服务器权威，`server.mjs` 每 `SNAPSHOT_MS=50` 用 setInterval 发快照；Windows 实测约 16 条/s（计时器粒度），每条约 0.8KB。
- 客户端 `net.js interpolate()`：每收到一条快照，从「当前渲染位置」线性插到新位置，固定 50ms 走完。
  下一条晚到（跨境抖动常见 100ms+）→ 单位停住 → 新快照一到再跳 → 体感卡顿。
- 手牌 / 法力已有本地预测（`session.js pending`），本次不动。
- 服务器在 Render 美西（Oregon），国内建连 6 次失败 2–3 次，TLS 握手 0.4–2.4s。

## A. 抖动缓冲插值（客户端为主，协议加一个字段）

1. `makeSnapshot` 加 `st`：服务器单调时钟毫秒（`performance.now()`）。旧服务器没有时客户端用到达时间兜底。
2. 客户端维护时钟映射 `off = st - now`：取最早到达的那条（`max`），晚到的按 EMA 缓慢回收（时钟漂移）；同时 EMA 统计迟到量 `jit`。
3. 渲染时间 `rt = now + off - delay`，`delay = clamp(60 + 3·jit, 100, 300)ms`：网络稳就延后 0.1s，抖就自动加大缓冲。
4. 每个单位存最近 6 个 `[st, x, z]`，在 `rt` 两侧样本间插值；缓冲吃完时按最后速度外推最多 100ms，再停。
5. 只影响单位位置；血量、事件、手牌照旧按到达即用（最多比位置早约 0.1s，可接受）。

验收：新增 `tests/interp.test.mjs`，模拟 0–150ms 随机迟到，断言渲染位置单调前进、单帧步长不超过匀速的 3 倍、无长时间冻结；`npm test` 全过；本地两窗口对局目测。

## C. Render 新加坡服务

- Render 不能改已有服务的区域，只能新建：同仓库、`node server/server.mjs`、Free、Region = Singapore、`TRUST_PROXY=1`。
- 新地址实测建连成功率 / 握手耗时，与美西对比；更好就把 `index.html` 的 `BG_ONLINE_URL` 与 Web 宇宙主页星球链接切过去。
- 旧美西服务先保留，停不停由用户决定。新服务同样需要推送后手动部署（同一仓库，两个服务都要点）。

## A 落地结果

- `net.js`：快照加 `sc`（服务器时钟；`st` 已被建筑占用，第一版撞名导致缓冲全为 NaN，已改名并加端到端测试）。
  缓冲时长按 25%/10% 速率平滑变化，避免抖动突增时画面倒退；外推上限 50ms。
- 同一组模拟抖动（迟到 0–150ms、TCP 成串到达）下对比：

| | 旧算法 | 新算法 |
|-|-|-|
| 冻结帧占比 | 42–44% | 基本为 0（单次最多 2 帧） |
| 最长冻结 | 112–128ms | ≤ 32ms |
| 最大单帧步长 | 3.6–4.4× 匀速 | < 3×，无倒退 |

- `tests/interp.test.mjs` 3 项（12 个随机种子 + 真实快照链路），`npm test` 104 项全过。
- 本地浏览器 + 机器人对手实测：缓冲稳定在 100ms，单位每 30ms 匀速前进。

## C 结论：不用做

Render 后台确认现有 `star-clash` 服务**本来就在 Singapore**。之前判断「美西」是看 DNS 别名 `gcp-us-west1-1.origin.onrender.com` 和响应头 `CF-RAY …-LAX` 得出的，错了：
LAX 是 Render 前面那层 Cloudflare 的洛杉矶节点。国内访问的实际路径是 国内 → Cloudflare 美国节点 → 新加坡源站，绕了太平洋一圈，这才是慢和不稳的原因。
所以换 Render 区域没有意义；要根本改善，需要国内能直连的服务器（香港 VPS，免备案），或不经 Cloudflare 海外节点的接入。新服务未创建。
